# Runbook — Update the WhatsApp Community Link

A short, repeatable flow for swapping the WhatsApp group invite link across the
whole site + backend emails. Follow it top-to-bottom whenever the invite changes.

The link is **not** stored in one single place — it lives in a few source files,
gets baked into compiled bundles + prerendered HTML, and is also embedded in the
backend confirmation emails. This runbook covers all of them.

---

## TL;DR

1. Find/replace the old invite URL with the new one in the **6 source files** below.
2. Run `npm run build` to regenerate the bundles + HTML.
3. Verify the old link is gone and the new one is present.
4. Deploy: hosting for the site, **and** Cloud Functions for the email links.

---

## Step 1 — Replace the link in the source files

Search the repo for the **old** invite URL and replace every occurrence with the
**new** one. As of the last update the links look like:

```
https://chat.whatsapp.com/<INVITE_CODE>
```

(An older link also had a `?mode=gi_t` query suffix — drop it unless WhatsApp gives
you one.)

Update these **6 source files** (do NOT hand-edit the generated files in Step 2):

| File | What it is |
| --- | --- |
| `site.config.js` | `brand.whatsappCommunity` — main source of truth for the site |
| `seo.config.js` | `externalUrls.whatsappCommunity` — SEO / structured data |
| `v2.jsx` | `V2_BRAND` fallback (used if config fails to load) |
| `app.jsx` | fallback inside a confirmation/share string |
| `functions/index.js` | **two** places — both confirmation-email templates |
| `llms.txt` | static "WhatsApp community" line for AI agents |

Quick way to locate every occurrence (run from repo root):

```bash
grep -rn "chat.whatsapp.com" . \
  --include="*.js" --include="*.jsx" --include="*.txt" \
  --exclude-dir=node_modules
```

---

## Step 2 — Rebuild the generated files

`index.html`, `roadmap.html`, `app.build.js`, and `v2.build.js` are **generated** —
never edit them by hand. Regenerate them from the updated sources:

```bash
npm run build
```

This runs two steps (see `package.json`):

- `build:js` → esbuild transpiles `app.jsx`/`v2.jsx` into `app.build.js`/`v2.build.js`
- `prerender` → Puppeteer renders the app and writes static `index.html` + `roadmap.html`

> If `node_modules` is missing, run `npm install` first.
> `masterclasses.html` and `about.html` are hand-authored static pages and are NOT
> regenerated by the build — they currently don't contain the link, but check them
> if that ever changes.

---

## Step 3 — Verify

Confirm the **old** code is fully gone and the **new** one is everywhere:

```bash
# Should return NOTHING:
grep -rn "<OLD_INVITE_CODE>" . --exclude-dir=node_modules

# Should list the source files + generated files (index.html, roadmap.html, *.build.js):
grep -rln "<NEW_INVITE_CODE>" . --exclude-dir=node_modules
```

Expected files containing the new link: `site.config.js`, `seo.config.js`, `v2.jsx`,
`app.jsx`, `functions/index.js`, `llms.txt`, `index.html`, `roadmap.html`,
`v2.build.js`, `app.build.js`.

---

## Step 4 — Deploy

Two separate deploy targets — both matter:

- **Website** (config, bundles, HTML, `llms.txt`): deploy Firebase Hosting.

```bash
firebase deploy --only hosting
```

- **Email links** (`functions/index.js`): the new link only reaches registration /
  confirmation emails after the Cloud Functions are redeployed.

```bash
firebase deploy --only functions
```

(Or `firebase deploy` to ship both at once.)

---

## Why it's spread across so many files

- `site.config.js` / `seo.config.js` are the human-editable source of truth.
- `app.jsx` / `v2.jsx` keep **fallback** copies so the app still works if the config
  file fails to load — these compile into the `*.build.js` bundles.
- `index.html` / `roadmap.html` are **prerendered** snapshots for SEO/no-JS crawlers,
  so the link gets frozen into them at build time.
- `functions/index.js` sends the link in transactional emails, independent of the site.

That's why a single change requires: edit sources → rebuild → deploy hosting + functions.
